**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Assumption: the implementation will anchor backend startup and dependency wiring in `src/backend/Program.cs`, keep the required solution entry at `src/backend/OuterloopLabApi.sln`, add feature-specific backend files under `src/backend` for the conversion endpoint, provider abstraction, audit model, and Cosmos repository, and anchor frontend changes in `src/frontend/index.html`, `src/frontend/src/main.tsx`, and `src/frontend/src/App.tsx` (or a new sibling component imported from `src/frontend/src/App.tsx`) so runtime `VITE_API_URL` replacement and the user-facing conversion workflow stay in the required folders.

**In Scope:**
- Add a backend `POST` API for a single real-time currency conversion request that accepts source currency, target currency, and amount, then returns the converted amount, normalized rate, provider marker data, backend execution timestamp, and a persisted audit identifier.
- Add a backend `GET` API to retrieve one previously recorded conversion audit entry by identifier from Cosmos DB.
- Persist a normalized audit document for each successful conversion containing the original request, normalized rate information, backend-generated execution timestamp, provider-supplied date or sequence markers, and the exact response values shown to the user.
- Add a frontend form in `src/frontend` that submits a conversion request to the backend and displays the immediate result plus the returned audit identifier and timestamps.
- Add a frontend retrieval flow that loads an existing conversion audit entry by identifier and renders the stored details clearly for audit review.
- Add targeted automated tests for successful conversion, audit retrieval, invalid input handling, and provider failure handling.

**Out of Scope:**
- Batch conversion uploads or multi-row settlement processing.
- Manual editing, deletion, or approval workflows for stored audit entries.
- Exchange-rate caching, scheduled prefetching, or historical rate analytics dashboards.
- User authentication, tenant administration, or role-based access control changes beyond the feature itself.
- Multi-provider routing, provider failover orchestration, or reconciliation against a second exchange-rate source.

**Feature Constraints:**
- Use `IHttpClientFactory` with a typed or named client for the external currency provider call so outbound HTTP behavior stays centrally configured and testable.
- Introduce an internal provider-normalization layer that maps arbitrary provider JSON into an internal result model containing at minimum `rate`, `providerDate`, optional provider sequence/reference metadata, and the normalized converted amount inputs used by compliance storage.
- Validate request currency codes as three-letter uppercase ISO-style codes and require `amount > 0`; invalid requests must return `ProblemDetails` with HTTP 400 and must not create an audit record.
- Represent monetary amounts and rates with `decimal`, and return the converted amount rounded to two decimal places in the API response and stored audit document using one consistent rounding strategy across backend and frontend display.
- Generate the backend execution timestamp once per successful request in UTC with fractional-second precision, persist that exact value, and return that same value in the success response so retrieval reproduces the original audit facts exactly.
- Translate upstream HTTP, timeout, schema-mapping, or unavailable-rate failures into a domain-specific `ProblemDetails` response with HTTP 503; do not bubble raw exceptions to clients and do not persist a partial audit record on those failures.

**Expected Outcome:** A user can submit a single conversion request from the frontend, receive an immediate backend-computed response, and later retrieve the same audited record by identifier. Concretely, if `POST` receives `fromCurrency = "USD"`, `toCurrency = "EUR"`, and `amount = 100.00`, and the normalized provider result is `rate = 0.92` with `providerDate = "2026-08-01"`, the API returns HTTP 200 with a payload that includes `convertedAmount = 92.00`, `rate = 0.92`, `providerDate = "2026-08-01"`, an `executedAtUtc` value such as `2026-08-01T14:03:22.481Z`, and a non-empty audit identifier. A follow-up `GET` for that audit identifier returns the same request values, rate, converted amount, provider marker values, and exact `executedAtUtc` timestamp from Cosmos DB. If the request uses `amount = 0` or an invalid currency code, the API returns HTTP 400 `ProblemDetails`. If the provider is unavailable or its response cannot be normalized, the API returns HTTP 503 `ProblemDetails` with a domain-specific message and no audit record is stored.

**Expected Agent Output:** OpenCode should produce an end-to-end implementation that updates `src/backend/OuterloopLabApi.sln` and `src/backend/Program.cs`, adds backend files for the conversion endpoint, provider client/normalizer, audit persistence model, and Cosmos repository/service, updates `src/frontend/index.html` and the relevant `src/frontend/src/*` UI/API files for conversion and audit retrieval, and includes automated tests that prove the success path, retrieval path, 400 validation path, and 503 provider-failure path.
